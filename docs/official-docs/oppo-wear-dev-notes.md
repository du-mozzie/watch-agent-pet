## 2 平台能力地图

### 2.1 四种接入形态

| 形态 | 说明 | 对本项目的意义 |
|---|---|---|
| 普通应用（APK） | 按手机开发思维开发，声明 watch feature | **主线**，Agent 桌宠就是这个 |
| 快应用 | 平台支持，无需安装包 | 可作为轻量入口，但生态与文档较少 |
| 小布语音技能 | 「一次开发实现多终端多场景触达」 | **可复用**：语音唤起可借小布，而不是自己抢按键 |
| 音乐控制器适配 | 音频类应用可适配，无需单独接 indicator | 若做"表冠当旋钮调音量"可参考 |

### 2.2 网络三通道（原文要点）

| 通道 | 条件 | 速度/限制 | 官方建议 |
|---|---|---|---|
| 蓝牙网络 | 手表与手机连接，共享手机网络 | **80KB 左右**（Q&A 另处写 80~120K） | **强烈建议使用 HTTPS**；强网络应用需做优化 |
| WLAN | 手表独立连 Wi-Fi | 同手机；**不支持需要认证的网络**（如酒店/公司 Portal） | 设置 → 网络与连接 → 打开 WLAN 添加 |
| eSIM | 开通后独立上网 | 同手机；区分独立号码与一号双终端 | 移动流量场景要提醒用户，避免额外费用 |

> 判读：80KB/s 这个上限决定了手表端**不能直传视频流**，Agent 桌宠的宠物动画必须本地预置，网络只传状态码和文本。语音也要考虑压缩（手表录音 → 低码率发送 → PC 转写）。

### 2.3 前后台机制（原文要点）

- **「出于功耗考虑，OPPO Watch 不支持应用在后台运行」**。有重要进程需后台，用**前台服务**（优先级高、不易被杀），并声明 `FOREGROUND_SERVICE`（普通权限，系统自动授予）。
- 前台服务功耗高，谨慎使用；功耗/内存过高仍会被系统杀掉。
- 长时间后台运行的应用（音乐、导航类）**应接入表盘顶部的 indicator**，提示用户"应用正在后台运行"，并提供快速返回入口。

> 判读：Agent 桌宠若要"Agent 一思考，手表就有反应"，本质上需要手表 App 常驻。在 ColorOS Watch 上这只有两条路：前台服务（带常驻通知/indicator）或用户每次手动打开。**这是产品形态的硬约束，不能假装不存在。**

## 3 两条接入路径（最重要的区分）

### 路径 A：上架官方软件商店

**5 步流程（原文）：**

1. 注册开发者
2. 申请权限
3. 创建手表应用（首页 → 产品列表 → 手表应用 → 创建应用，填名称和包名）
4. 提交审核
5. 上架

**提交审核需要准备的材料（原文清单）：**

| 材料 | 具体要求 |
|---|---|
| APK | 上传后自动解析包名与应用名 |
| 一句话简介 | 简要说明功能与特点 |
| 软件介绍 | 主功能 + 操作步骤 |
| 版本说明 | 本版更新内容 |
| 隐私政策网址 | 若与其他终端共用，须在文本中说明**手表端**收集使用个人信息的目的、内容、方式和范围 |
| 年龄分级 | 按平台标准选择 |
| ICON | **120×120 px，方形，PNG，<1MB**，须与安装包内图标一致 |
| 截图 | **3~5 张，402×476 px，JPG/PNG，单张 <1MB**，须去手表边框，不得用其他品牌手表作边框 |
| 版权证明 | **软著扫描件**；无软著则提供 1~3 个其他市场后台上架截图；再无则提供手机端对应应用软著 |
| 联动信息 | 是否需手机端配合（扫码登录/付费/手机点击后手表继续） |
| 测试报告 | .xlsx，须含测试用例 |
| 测试辅助说明 | 账号密码、设备配置要求等 |
| 商务联系人 | 便于审核沟通 |

**时间：** 测试人员 **3~10 个工作日**审核；超过 10 个工作日可联系在线客服催审。**审核通过后自动发布，不支持定时发布。**

### 路径 B：侧载调试（本项目主线）

- 只需：开发者模式 + USB 调试 + 充电底座连线。**不经过审核，不需要软著、不需要 ICON 规格、不需要 5 步流程。**
- 但仍然受**系统本身**的限制（不能装 64 位、不能改系统分区、不能换表盘）。

### 关键判读：审核规范 ≠ 技术边界

这是整份资料里最容易误判的地方，必须分清两类约束：

| 约束类型 | 例子 | 侧载能否绕过 |
|---|---|---|
| **审核条款**（上架门槛） | 「不占用导航键/功能键」「禁止开机自启」「应用内不得下载安装其他应用」「必须能右滑返回」 | **能**。侧载不经审核 |
| **系统策略/功耗机制** | 「不支持应用在后台运行」「后台持有 sensor 每次最长 1s」「非 IM 类禁止后台联网」「唤醒锁禁止」 | **不能**。这是 ROM 层的行为，审核只是把系统事实写成了条款 |

所以：想绑物理按键做语音键，侧载可行但违背官方设计意图（官方原文称「功能暂不对外开放」）；而想让手表 App 后台持续联网收 Agent 状态，**侧载也做不到**，只能前台服务。

## 4 Wear Engine SDK：手机 ↔ 手表通道

### 4.1 定位（原文）

> 「OPPO Wear Engine SDK 面向手机和穿戴设备的应用与服务开发者，提供 OPPO 穿戴设备开放能力。开发者通过调用 Wear Engine SDK 开放能力，可以实现**手机上的生态应用与服务，给穿戴设备发消息、发通知、传输数据，并获取穿戴设备状态、读取传感器数据**等，也可以实现**穿戴设备上的生态应用与服务，给手机发消息、传输数据**等。」

**能力矩阵：**

| 方向 | 能力 |
|---|---|
| 手机 → 手表 | 发消息、发通知、传输数据、拉起手表端应用 |
| 手机 ← 手表 | 收消息、收数据、**读取传感器数据**、获取设备状态（型号/SKU/ColorOS Watch 版本/系统版本/佩戴状态） |
| 鉴权前提 | 访问接口需**校验访问应用的包名与签名** |

### 4.2 健康数据字段（原文表格）

| 个人信息类型 | 字段 | 用途 | 存储 |
|---|---|---|---|
| 设备信息 | 蓝牙连接列表 | 获取已配对设备列表 | 本地不存储，不上云 |
| 设备信息 | 手机系统版本；穿戴设备型号、SKU、ColorOS Watch 版本、系统版本号、使用信息、**佩戴状态** | 订阅设备状态、传输数据 | 本地不存储，不上云 |
| 应用信息 | 应用安装状态 | 判断对端应用状态 | 本地不存储，不上云 |
| **健康数据** | **最近心率、每日活动数据（运动步数、运动距离、爬楼数、锻炼时间）、睡眠数据、心电图数据、血氧数据** | 获取设备健康数据 | 本地不存储，不上云 |

> 判读：字段是"**最近心率**"，不是"心率流"。配合「订阅」权限定义（见下），可以理解为**事件级推送**：手表测到新值就推一次，而不是按固定频率采样。这就是"实时"只能做到"每次测量时更新"的根源。

### 4.3 权限模型（原文表格）

| 权限 | 用途 | 开启前是否询问 | 是否可关闭 | 关闭后影响 |
|---|---|---|---|---|
| **设备间数据交换** | 与其他设备上的应用交换数据 | 是 | 是 | 应用无法在设备间通信 |
| **健身运动** | **查询并订阅**设备上运动和健康数据 | 是 | 是 | 应用无法获取设备上的运动和健康数据 |

**SDK 自身不涉及额外系统权限**，但访问接口前需要：访问网络 + 获取应用列表（用于与服务器鉴权校验），均为开机权限声明。

### 4.4 用户关闭路径（原文）

- **手机端**：健康 App → 个人头像 → 个人中心 → 隐私保护中心 → **设备数据权限管理**
- **手表端**：设置 → 其他设置 → 应用管理 → 应用列表 → 应用 → 应用权限 → **其他权限**

> 判读：这条路径对开发调试很有用——如果 SDK 拿不到数据，先来这里确认权限是否被关。也说明**权限控制在用户手里**，不是开发者能强开的。

### 4.5 合规与存储

- SDK 作为**数据的委托处理者**，不是处理者；数据用途由接入方（你）决定并负责。
- **数据不在设备终端存储，也不上传服务器**（SDK 层面）。
- 接入前须签《OPPO Wear Engine SDK 使用协议》《个人信息处理协议》，并在自己的隐私政策中显著告知用户。
- 不以 14 周岁以下儿童为服务对象。

## 5 健康服务 SDK：健康 App ↔ 第三方

### 5.1 定位（原文）

> 「OPPO 健康服务是为开发者提供**查询用户穿戴设备数据**的能力，在接入服务且获得用户授权后，开发者能够快速获取运动健康相关数据。」

通道模型与 Wear Engine 不同：**不是手机 App 直连手表，而是由「健康 App」把数据共享给第三方 App。**

### 5.2 传输字段（原文表格）

**正向：健康 APP 传输给第三方**

| 类型 | 字段 | 必要/可选 |
|---|---|---|
| 个人身份类 | ssoid 映射后形成的虚拟用户 ID（用于账号绑定） | 必要 |
| **运动健康数据** | **压力、心率、心电记录、睡眠、血氧、步数、消耗、锻炼时长、活动次数、运动记录** | **可选**（开发者和用户可选） |

**反向：第三方传输给健康 APP**

| 类型 | 字段 | 必要/可选 |
|---|---|---|
| 运动数据 | 运动记录（数据同步写入） | 可选 |
| 设备信息 | 穿戴设备 MAC 地址（标识设备） | 必要 |

### 5.3 其他要点

- **SDK 不会调用任何权限。**
- 授权管理路径：健康 App → 个人头像 → 个人中心 → **「数据共享与授权」** → 选择对应第三方应用授权/查看/取消。
- 同样本地不存储、不上云、境内服务器、不以儿童为服务对象。

> 判读：这套字段比 Wear Engine **更全**（多了压力、消耗、活动次数、运动记录），但它是"健康 App 共享"模式，实时性更弱、更像历史聚合。适合做健康看板的长周期趋势，不适合做"此刻心率"。

## 6 两套 SDK 的选择

| 维度 | Wear Engine SDK | 健康服务 SDK |
|---|---|---|
| 核心场景 | 手机↔手表双向通信、设备状态、传感器数据 | 查询穿戴设备健康数据 |
| 数据来源 | 直连穿戴设备 | 健康 App 中转共享 |
| 实时性 | 相对好（订阅推送） | 较弱（共享/聚合） |
| 字段 | 最近心率、活动、睡眠、ECG、血氧 | 压力、心率、心电记录、睡眠、血氧、步数、消耗、锻炼时长、活动次数、运动记录 |
| 权限 | 设备间数据交换 + 健身运动 | 无系统权限，用户授权共享 |
| 适合本项目 | **Agent 状态通道 + 手表控制**（主线） | **健康看板的历史/聚合数据** |

**建议：两者都接。** Wear Engine 承担"桌宠与 Agent 的双向对话"这条主干；健康服务 SDK 承担"桌面看板要的历史趋势"这条支线。不要指望单靠其中一个覆盖全部。

## 7 开发硬约束清单

### 7.1 交互规范（原文）

| 交互 | 说明 |
|---|---|
| 单击 | 最常用，选择、启动应用、触发功能 |
| 双击 | 一般用于放大图片或地图 |
| 长按 | 低频复杂操作（长按编辑、删除）；运动界面长按结束以防误操作 |
| 拖动 | 低频操作（向上拖动删除、Applist 拖动排序） |
| 捏 / 拉 | **手表屏幕小，多点触控困难，不建议使用** |
| 全局右滑 | 系统全局响应右滑退出或返回上一层级；滑动超过屏幕一半响应返回 |
| 左右滑 | 非左边缘区域可左右滑切换应用内功能界面，多页面建议加翻页符 |
| 上滑/下滑 | 表盘界面下滑进控制中心、上滑进通知中心；应用页面长按屏幕边缘可呼出控制中心/通知中心 |
| **导航键（上键）** | **用户应用与 Applist / 表盘直接切换，不能用于其他功能** |
| **功能键（下键）** | **用于开关机、快捷拉起应用、最近任务，一般不用于应用内功能，功能暂不对外开放** |

> 判读：这是本项目最重要的一条硬件约束。**官方明确把两个物理键用途锁死了**，而且写明"暂不对外开放"。Agent 桌宠要的"按住语音键录音"、"长按 SW2/SW3"，在官方语义里没有对应键位。侧载技术上能拿到 keycode，但那是"越界使用"，且官方随时可能在后续系统版本里改掉。

### 7.2 功耗规范（审核规范原文逐条）

**应用设计：**

| 编号 | 条款 |
|---|---|
| 1.1 | 禁止频繁使用非唤醒 alarm，**一小时内最多 1 次** |
| 1.2 | 灭屏情况下**禁止申请非唤醒 alarm** |
| 1.3 | 除 IM 类和即时通知业务外，**禁止申请非用户设置的唤醒 alarm** |
| 1.4 | 闹钟类应用仅允许用户设置的唤醒 alarm |
| 1.5 | **禁止申请持有唤醒锁** |
| 1.6 | **除 IM 类应用外，禁止在后台进行联网行为** |
| 1.7 | 除在线音频类外，禁止后台大流量访问，**1 小时最大 10MB** |
| 1.8 | 禁止在后台长时间持有 sensor，**每次最长持有 1s** |
| 1.9 | **除导航类和健康类外，禁止在后台频繁持有 sensor，最多 1 分钟 1 次** |
| 1.10 | 导航类和健康类后台循环持有 GPS，**建议 1s/次上报** |
| 1.11 | 禁止使用各种保活手段让应用常驻后台 |
| 1.12 | 后台任务应使用 service |
| 1.13 | 后台定时任务应使用 jobschedule |

**准出标准：**

| 编号 | 条款 |
|---|---|
| 2.1 | 需网络业务页面电流 **<60mA**；不需网络页面 **<30mA** |
| 2.2 | 动态界面电流 **<120mA** |
| 2.3~2.7 | 音频：灭屏本地 ≥4.5h、亮屏本地 ≥3h、灭屏在线 ≥5h、亮屏在线 ≥3.5h |

**稳定性准出：** 30 万次延时 500ms 的 Monkey，log 中 crash 与 ANR **各不超过 3 个**，无内存泄漏。

> 判读三条硬结论：
> 1. **「除 IM 类应用外，禁止在后台进行联网行为」** —— Agent 桌宠要"随时接收 Agent 状态"，本质就是后台联网。上架语境下必须把自己论证成 IM/即时通知类，或改成前台服务。侧载也受系统功耗策略约束。
> 2. **「后台持有 sensor 每次最长 1s」+「非健康类最多 1 分钟 1 次」** —— 侧载直读心率只能"抓 1 秒、放掉、等一分钟再抓"，做不了连续曲线。这解释了为什么"秒级心率"必须进运动模式。
> 3. **「禁止持有唤醒锁」+「禁止保活」** —— 不要指望靠保活让手表 App 永远活着。

## 9 对本项目的逐条映射

把上面所有条款落到"Agent 桌宠六项能力"上：

| 需求 | 官方通道 | 判定 | 风险 / 绕法 |
|---|---|---|---|
| **Agent 状态跟随** | Wear Engine：手机→手表发消息/发通知 | ✅ 可做 | 手表端必须在前台或前台服务；「非 IM 类禁止后台联网」是最大障碍 |
| **语音输入** | 手表录音 → 手机/PC 转写 | ✅ 可做 | 录音属前台行为，问题在"按哪个键"——物理键被锁 |
| **实时对话** | Wear Engine 双向 + 长连接 | ⚠️ 有限 | 后台联网受限；蓝牙网络 80KB/s 只够文本 |
| **形象与音效** | App 内资源包 | ✅ 可做（App 内） | ❌ 固件级下发不可能（无固件控制权） |
| **组件中心** | 资源 / 脚本级组件 | ⚠️ 受限 | ❌ 不能装 APK（禁 INSTALL_PACKAGES）；只能做 JSON/脚本/图片级 |
| **设备设置** | App 内音量、城市 | ⚠️ 部分 | Wi-Fi 配对须跳系统设置，第三方无权代配 |
| **健康数据看板** | Wear Engine + 健康服务 SDK | ✅ 可做 | 实时性取决于手表采样节奏；见 §4.2 判读 |

### 三条不可回避的硬结论

1. **Agent 桌宠的"常驻"在 ColorOS Watch 上没有官方正解。** 前台服务能做，但要带 indicator / 常驻通知，且功耗会被限制。产品叙事应该是"一键唤起的宠物 App"，不是"永远活着的桌宠"。
2. **物理键（上键/下键）在官方语义里不属于第三方应用。** 语音键只能落在屏幕内（长按屏幕某区域），或者侧载越界拿 keycode（有被后续系统版本改掉的风险）。
3. **"实时"是采样节奏问题，不是技术问题。** 官方产品页写的「能够提供毫秒级的运动、健康数据」是营销口径，不等于第三方 App 能拿到毫秒级流。真实边界见 §4.2。

## 11 下一步（等底座回来再做）

底座到位后，按这个顺序跑，一条命令对应一个结论：

```powershell
# 0 工具就位
adb version

# 1 设备是否被识别（手表放底座、开 USB 调试、表上点"允许"）
adb devices

# 2 系统基线
adb shell getprop ro.build.version.sdk      # 验证是否真为 29（Android 11）
adb shell getprop ro.product.cpu.abi        # 验证是否 armeabi-v7a（只支持 32 位）
adb shell wm size                           # 应为 378x496
adb shell wm density                        # 确认是否 320

# 3 【最关键】手表到底向系统暴露了哪些传感器
adb shell dumpsys sensorservice | findstr /i "0x"
# 看点：除标准 TYPE_HEART_RATE 外，有没有血氧 / 腕温 / ECG 的私有 sensor 类型
# 有 → 侧载直读可行；没有 → 血氧/ECG 只能走官方 SDK

# 4 物理键 keycode（分别按功能键、转表冠、按表冠）
adb shell getevent -l

# 5 当前前台窗口（验证侧载 App 能否正常起）
adb shell dumpsys window | findstr mCurrentFocus
```

**预判（待实测推翻或确认）：**

| 探针 | 我的预判 | 依据 |
|---|---|---|
| `ro.build.version.sdk` | 30（Android 11） | 开放机型表写 Android 11 |
| `ro.product.cpu.abi` | `armeabi-v7a`（可能带 `armeabi-v7a,armeabi`） | 社区实测只能装 32 位 |
| 心率 sensor | ✅ 有（标准 TYPE_HEART_RATE） | Android 标准 API 必存 |
| 血氧 sensor | ❓ 未知 | Android 无标准 SpO2 API，看厂商是否暴露私有类型 |
| 腕温 sensor | ⚠️ 可能有 | 社区有人用第三方 App 读到过腕温 |
| ECG sensor | ❌ 大概率无 | 需电极 + 厂商算法，一般不开放 |

跑完把输出贴回来，我据此定"路径 A（SDK 手机中转）还是 路径 B（侧载直读）"为主。

## 12 个人自用口径（非商业、不上架）

> **前提：只装自己的一块表，不对外分发、不进软件商店。**
> 在此前提下，第 3 节（接入流程）、第 7.3 节（审核红线）、第 7.2 节的准出标准大部分**直接失效**。以下按"哪些能划掉、哪些还得管"重新算一遍。

### 12.1 可以整段划掉的

| 项 | 原要求 |
|---|---|
| 软著 / 版权证明 | 上架必交，自用不需要 |
| ICON 120×120、截图 402×476、素材源文件 | 不需要 |
| 隐私政策 8.1~8.13 全套 | 平台审核项，自用不需要（自己知道数据去哪就行） |
| 测试报告 .xlsx、30 万次 Monkey（crash/ANR 各 ≤3） | 不需要 |
| 3~10 个工作日审核、自动发布、催审客服 | 不需要 |
| 应用名称 1.1~1.16（不得含"官方/正版"、≤20 汉字等） | 不需要 |
| 功耗准出 60/30/120mA、音频 3~5h | 从"准出红线"降级为"自己参考的省电目标" |
| 商务联系人、宣传素材授权邮件 | 不需要 |

### 12.2 仍然生效的（跟商不商业无关）

| 约束 | 性质 | 说明 |
|---|---|---|
| 只能装 **32 位 APK**（armeabi-v7a） | ROM/框架 ABI | 没有 64 位运行环境，装不上就是装不上 |
| 不支持应用在后台运行 | 系统后台策略 | 仍需前台服务 + indicator 提示 |
| 屏幕 378×496、DPI 320、约 189×248 dp | 硬件 | 与审核无关 |
| 蓝牙网络约 80KB/s | 硬件 | 与审核无关，决定只能传文本/状态 |
| 不能换表盘、不能改系统分区、不能刷机 | 系统封闭性 | 与审核无关 |
| **拿不到 `INSTALL_PACKAGES`** | Android 权限模型 | 普通应用无此权限（需系统签名）。**组件中心仍不能自己静默装 APK**，这条不是审核条款，绕不过 |

### 12.3 从"受限"升级为"可以做"

| 项 | 之前判定 | 自用口径下 |
|---|---|---|
| 物理键绑语音（按住录音） | ⚠️ 审核禁止占用导航键/功能键 | ✅ **侧载不受审核约束**，可以用 `getevent` 拿到 keycode 自己响应；仅需实测确认能监听到 |
| 开机自启 | ⚠️ 审核禁止 | ✅ 可做（不优雅但能跑） |
| 后台常驻 | ⚠️ 受"非 IM 类禁止后台联网"约束 | ⚠️ 仍需前台服务，但**不用担心被审核打回**；能跑多久取决于系统杀后台的力度，要实测 |
| 组件中心 | ❌ 不能装 APK | 仍不能**自动**装，但可以"**adb 手动装 + App 内热加载资源包**"（图片/JSON/脚本级） |
| 首次启动声明页 | ⚠️ 必须有 | 可省 |
| 右滑返回 | ⚠️ 必须实现 | 建议保留（否则自己用着难受），但不是硬性要求 |

### 12.4 唯一还需要走官方流程的地方

**Wear Engine SDK / 健康服务 SDK 的鉴权。**

- 原理：SDK 访问接口时**校验包名 + 签名**，校验在 OPPO 服务端完成，本地绕不过。
- 所以即使不上架，也要：**注册开发者（支持个人实名）→ 申请穿戴/健康权限 → 用你的包名签名换取鉴权**。
- **不确定项**：个人开发者能否通过"健康数据"类权限申请（部分平台对资质有要求）。这是**唯一值得提前问客服**的点，问一句 `watchapp@oppo.com` 或在线客服即可。

> 换句话说：**不想碰 SDK，就纯侧载 + `SensorManager` 直读，完全不用注册任何账号**——代价是血氧/ECG 能不能读到未知（见 §11 探针 3）。想稳拿血氧/ECG/睡眠，才需要走 SDK。

### 12.5 侧载自用的风险（说实话）

| 风险 | 程度 | 应对 |
|---|---|---|
| 合规 | 低。自己做、自己装、只给自己用，不构成分发 | 不对外传播 APK 即可 |
| 保修 | 装第三方 App 一般不影响硬件保修；但**一旦 root 或改系统分区**，出故障可能被拒保 | 坚持不 root、不改分区的底线 |
| 系统升级覆盖 | 固件升级可能清掉侧载应用或重置权限 | 备份 APK + 配置；升级后重装 |
| 变砖 | 侧载本身不会变砖（不碰系统分区） | 不做刷机类操作 |

### 12.6 结论：从"审核导向"切到"体验导向"

- **不用为"能不能过审"做任何设计**，只为"好不好用 + 耗不耗电"设计。
- 唯一需要自我克制的仍是**功耗**——不是因为审核，是 570mAh 的电池真不经折腾。全智能模式标称 5 天，一个常驻前台服务 + 高频传感器就能把它拉到 1~2 天。
- 原设计调研文档里"六项能力"的判定，在自用口径下可以把 §9 表格中的 ⚠️ 项逐个重新评估，判定会更宽松。
