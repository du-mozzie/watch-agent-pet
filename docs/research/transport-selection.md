# 通信通道选型（v1，2026-11-19）

> 本文保留 OPPO 场景的历史假设和选型，不代表已实现能力。最新模块边界以 [v3 总体架构](architecture.md)为准，协议以[当前草案](../../contracts/protocol.md)为准。

> 场景前提：**白天佩戴**是主场景（健康数据 + 宠物状态），表放桌上/充电底座是次场景。
> 本文回答「手表 ↔ PC 用什么协议」，结论先行：**桥接层双通道：BLE 优先（近场、佩戴场景）+ Wi-Fi 局域网备选（固定工位）**，上层协议统一。

---

## 1 需求与流量画像

| 流量 | 方向 | 量级 | 频率 |
|---|---|---|---|
| 健康数据帧 | 手表 → PC | 每帧 <1KB（聚合后） | 每分钟~每秒级 |
| Agent 状态（后期扩展） | Agent 来源 → PC | <200B/帧 | 事件驱动（不下发手表） |
| 宠物控制（点按/语音起止） | 手表 → PC | <100B | 事件驱动 |
| 语音音频 | 手表 → PC | 低码率压缩后 ~16KB/s | 会话中 |

总带宽需求 <100KB/s 峰值。**任何 BLE 4.2+（~几十 KB/s~百 KB/s 级）都够用**；不需要经典蓝牙速率。

## 2 候选通道对比（市场方案调研）

| 通道 | 市场主流场景 | 功耗 | 佩戴场景适配 | 关键风险 |
|---|---|---|---|---|
| **BLE GATT** | 智能穿戴标配（Zepp 华米、华为鸿蒙穿戴手机↔手表、ESP32 配网）：连接建立 3ms、功耗比经典蓝牙降 90% | 极低（可维持常连） | ✅ 最佳 | **ColorOS Watch 第三方 App 能否开 GATT server 未验证**（Android 11 标准能力理论可行，需真机 PoC P9） |
| Wi-Fi 局域网 | 视频类高带宽场景 | 高（表电池小） | ⚠️ 耗电快、出网段即断 | 已验证 adb tcpip 可用，数据链路技术可行 |
| 蓝牙经典 SPP | 老式串口透传 | 高 | ⚠️ | Android 11 第三方可用性存疑 |
| eSIM/公网 | 独立通话场景 | 高+流量费 | ❌ | 服务器中转增加复杂度 |
| 官方 Wear Engine（手机中转） | OPPO 生态应用 | 手机侧耗电 | ⚠️ 需手机常在+注册开发者 | SDK 鉴权要走官方流程 |

参考：鸿蒙穿戴架构（华为开发者官网）即手机与手表 BLE 直连做运动健康/消息同步；华米 Zepp 生态同样 BLE 为干道。**"佩戴设备 ↔ 主机"的市场共识就是 BLE。**

## 3 决策

1. **上层协议不变**：健康帧 JSON、<4KB/帧、带序号与 ACK——通道无关，做成可插拔 transport。六态事件模型（`idle|thinking|running|waiting|done|error`）保留为协议扩展位（Agent 来源 → PC，后期扩展；2026-11-19 起不下发手表）。
2. **通道层双轨**：
   - **主：BLE GATT**（手表做 peripheral，自定义 Service，PC/手机做 central）——待 P9 真机验证（ColorOS Watch 第三方 App 的 GATT server 可用性、后台广播限制）
   - **备：Wi-Fi 局域网 TCP/WebSocket**（PC 固定工位场景；已验证 adb tcpip 走通）
3. **自动降级**：BLE 断 → 缓存 → 恢复补传（健康帧带序号）；工位场景可手动切 Wi-Fi。
4. **eSIM/公网不做**（数据不上云原则 + 流量费）。

## 4 新增 PoC

- **P9（新增）：ColorOS Watch 第三方 App BLE GATT server 可行性**——手表端 `BluetoothGattServer` 起自定义服务 + 广播，PC 端（WinRT API）扫描连接读写 Notify。通过 → 主通道定为 BLE；不通过 → 回退 Wi-Fi 为主。
