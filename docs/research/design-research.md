# OPPO Watch 4 Pro × Agent 桌宠：设计调研

> 本文保留 OPPO 场景的历史假设和选型，不代表已实现能力。最新模块边界以 [v3 总体架构](architecture.md)为准，协议以[当前草案](../../contracts/protocol.md)为准。

> 目标：以现有 OPPO Watch 4 Pro 的硬件为基础，复刻 HachimoDock 类「AI Coding 陪伴设备」的六项能力（Agent 状态跟随 / 语音输入 / 实时对话 / 形象与音效 / 组件中心 / 设备设置），同时**完整保留手表原有功能**，并支持对接 codex、claude code、qoder、豆包、workbuddy 多个 Agent 客户端。
>
> 调研时间：2026-11-17　｜　结论均基于公开资料 + 官方开发文档推断，标注「待实测」的项必须在真机上验证后才能进入开发。

---

## 0. 结论先行

1. **技术上可行，但必须更换实现方式。** OPPO Watch 4 Pro 不是 ESP32 类可刷固件设备，而是**不可刷机的 ColorOS Watch（AOSP 定制）**。因此不能"写固件"，只能"**侧载一个 Android App + 电脑端桥接守护进程**"。这条路恰好天然满足"保留原始功能"——不动系统分区、不 root、不换桌面。

2. **六项能力中 4 项可做到接近原设计，2 项必须降级：**
   - 可做：Agent 状态跟随、语音输入、实时对话、组件中心（工程量最大）
   - 降级：**形象与音效**（"兼容固件独立下发音效"无法实现，只能 App 内播放）、**设备设置**（Wi-Fi 配对第三方 App 无权直接完成，只能引导跳转系统设置）

3. **最大的风险不在软件，而在三个系统黑盒**：① 物理按键事件能否被第三方 App 截获 ② 后台/息屏保活 ③ 局域网长连接稳定性。这三项决定项目成败，建议 **先做 1～2 周的 PoC，再决定是否投入**。

4. **硬件不匹配点（相对 HachimoDock）**：按键 3+摇杆 → 2（表冠 + 功能键，且表冠长按被系统关机菜单占用）；屏幕 2.8" 480×640 → 1.91" 378×496（≈189×248 dp，可用面积约为原型机的 40%）；无自定义固件；**不能替换表盘**。

5. **五个 Agent 的接入能力差异很大**：Claude Code、Qoder、Codex 走官方 hooks，可拿到完整事件（思考/工具/等待/完成/错误）；WorkBuddy 只能 tail 本地日志；豆包 PC 客户端没有公开 hooks，只能做粗粒度猜测。这直接对应原设计里那句"事件完整程度取决于 Agent 适配器"。

## 1. 参照系确认：你这份清单的原型是 HachimoDock

你列出的六条能力（含"宠物页面长按 SW2""组件中心 PetUI""兼容固件独立下发音效"）与小米技术委孵化的开源硬件 **HachimoDock（哈基米机）** 高度一致，可确认是同一套设计语言：

| 项目 | HachimoDock 原始设计 | 来源 |
|---|---|---|
| 主控 | ESP32-P4，32MB Flash + 32MB PSRAM | 公开报道 |
| 屏幕 | 2.8 英寸，480×640 | 公开报道 |
| 交互 | 3 个实体按键 + 四向摇杆 + 麦克风 | 公开报道 |
| 语音链路 | **录音上传电脑端做识别**，再把文字送进 Codex / WorkBuddy 会话 | 公开报道 |
| 组件 | PetUI，声明式组件 + 自然语言生成，含番茄钟/喝水提醒/小游戏/电脑状态 | 公开报道 |
| 形象 | 内置形象 + AI 生成 + 社区导入 + 本地视频导入 | 公开报道 |
| 同步 | 电脑端通过 **USB** 同步状态、形象、组件 | 公开报道 |
| 客户端 | Windows x64 / Apple Silicon Mac；不内置语音与生成服务密钥 | 公开报道 |
| 许可 | 开源，允许个人非商业复刻、修改、组件创作 | 公开报道 |

**可以借鉴什么**：PC 端协议、状态机、适配器思路、组件描述格式、形象资源格式——这些与硬件无关，可直接复用。
**不能借鉴什么**：固件、屏幕驱动、按键驱动、音频子系统——全部要重写。

另一个有用的现成资产：**Petdex** 的宠物包格式（`pet.json` 定义 9 种动画状态 + `spritesheet.webp` 横向条带），且其社区已有"水豚噜噜"形象条目。手表端可直接吃这套格式，省掉美术重画；它的桌面端还提供了一个可参考的本地协议：在 `127.0.0.1:7777` 起 HTTP server，用 `~/.petdex/runtime/update-token` 做鉴权，`POST /state` 推状态——这套做法在手表桥接里可以沿用。

## 2. 硬件底座画像

### 2.1 规格

| 维度 | 参数 |
|---|---|
| SoC | 骁龙 W5（全智能）+ 恒玄 2700（轻智能 RTOS） |
| 内存/存储 | 2GB RAM + 32GB ROM |
| 系统 | ColorOS Watch 6.0（AOSP 定制，**非 Wear OS**） |
| 屏幕 | 1.91" LTPO AMOLED 柔性曲面，378×496 px，326 ppi |
| 机身 | 50.1×38.3×12.85 mm，52.3 g，5ATM |
| 电池 | 570 mAh，全智能 5 天 / 轻智能 14 天，10 分钟充到约 24h |
| 连接 | 蓝牙 5.0、Wi-Fi 2.4G/5G（802.11 a/b/g/n）、eSIM、NFC |
| 输入 | 触摸 + 表冠（可旋转、可按压）+ 侧边功能键 + ECG 电极键（**不可按压**）|
| 输出 | 扬声器、Z 轴线性马达 |
| 采集 | 麦克风、心率/血氧/ECG/腕温/气压/地磁/加速度/陀螺仪/环境光 |

### 2.2 开发可达性（已确认可用）

- **开发者模式**：按导航键进 Applist → 设置 → 其他设置 → 关于手表 → 版本号连点 7 次 → 返回"其他设置"出现"开发者选项" → 开 USB 调试。
- **调试方式**：手表放充电底座，底座接电脑/手机，用 ADB 工具连接（会弹授权框）。
- **侧载已证实可行**：社区已在 Watch 4 Pro 上跑通 AAPS、动态血糖、微信、ZeroTermux、Clash、第三方桌面等复杂应用，说明**网络、传感器、文件系统、后台进程都可被第三方 App 使用**。
- **官方开发口径**：「手表是 Android 系统，不是 Android Wear，按手机开发思维开发」，需声明 `android.hardware.type.watch`，并实现右滑返回（`android:windowSwipeToDismiss`）。
- **按键可自定义**：系统设置里可将侧键指定为"快捷启动某个应用"——这是把宠物 App 做成"一键直达"的官方合法入口。

### 2.3 开发约束（会直接改设计）

| 约束 | 影响 |
|---|---|
| **只支持 32 位 APK**（armeabi-v7a），不能装 64 位 | 所有 native 依赖必须有 32 位构建；Wasmtime/V8 这类重型 runtime 基本排除，只能用 wasm3 / wasmi / QuickJS 级别 |
| **DPI 默认 320**，改 DPI 会影响全系统 UI | 设计画布按 189×248 dp 做，不要靠改 DPI 腾空间 |
| 曲面屏边缘有裁切 | 实际安全区估计约 180×235 dp，四角与左右边缘要留边 |
| 蓝牙网络带宽仅约 80～120 KB/s | 走蓝牙代理时**不要传图片/音视频**，只传文本与小图标 |
| 双芯架构：App 只跑在骁龙 W5 侧 | 进入"轻智能模式"时 App 停止运行，状态栏/宠物消失（这是硬限制，不是 bug） |
| 不能刷机、不能改表盘格式 | 宠物**不能成为表盘**，只能作为 App / 快捷入口 / 通知 |

## 3. 系统开放性的三条硬边界

### 3.1 不能替换表盘 → "宠物常驻桌面"要重新定义

OPPO 表盘是私有格式，只从表盘商店下发，第三方无法注册表盘。所以"抬腕即见水豚"只能通过以下三种降级形态实现：

1. **App 快捷入口**（推荐）：用系统"自定义硬件按键"把功能键指向宠物 App，按一下即进，退出手势右滑。
2. **第三方桌面**：技术上能装（如 Square Home），但社区实测"Watch 4 Pro 对第三方桌面很不友好"，会破坏原系统体验，**与"保留原始功能"目标冲突，排除**。
3. **通知/表盘小组件**：表盘小组件是 OPPO 自有能力，第三方无法注册；通知无法自定义布局，只能显示文字。**仅作兜底**。

结论：产品叙事要从"手表桌面变成宠物"改成"**宠物是一个随时一键唤起的 App，退出即回到原生手表**"。

### 3.2 只能 32 位 → 组件中心的 runtime 选型被锁死

- 声明式组件：JSON → 原生 Compose/自绘渲染，或单页 WebView。轻量、可控。
- 脚本/WASM 组件：**必须选有 32 位 ARM 构建的 runtime**。可行候选：`wasm3`（纯 C，易交叉编译）、`wasmi`（Rust，可编 32 位）；不可行：`wasmtime`（体积与 ABI 都不合适）、Node/V8。
- 更务实的替代：用 **QuickJS（32 位）** 做脚本组件，把"WASM 组件"降级为"JS 组件"。对用户可感知的差异很小。

### 3.3 权限收紧 → 需要"半提权"工具链

ColorOS Watch 对第三方 App 权限管得很紧（社区共识："OPPO 手表的权限很难给全"）。已知可行路径：

- **Shizuku**：通过 ADB 激活，让 App 以 shell 权限调用部分系统 API。
- **Dhizuku / AppOps**：补齐悬浮窗、修改系统设置、读取使用情况等敏感权限。
- 这套流程**只在首次配置时需要**，可以打包成一个"一键配置脚本 + 图文引导"给用户。

风险提示：这些工具属于社区方案，系统升级后可能失效，需要做降级兜底（权限拿不到时，功能自动收敛到不需要权限的部分）。

## 4. 六项能力逐条落地判定

| # | 原设计描述 | 在 Watch 4 Pro 上的实现 | 判定 | 关键风险 / 备注 |
|---|---|---|---|---|
| 1 | **Agent 状态跟随**：思考/执行/等待/完成/错误呈现在动画与任务气泡，完整度取决于适配器 | 手表 App 内四区布局（状态灯+状态名 / 形象 / 任务气泡 / 操作区），状态由 PC 桥接推送；形象按状态切图（Petdex 9 状态可映射到 5 态） | ✅ 可行 | 依赖长连接与保活；气泡文本要截断，189dp 宽度约 12～14 个汉字/行 |
| 2 | **语音输入**：按住语音键录音，松开识别并**追加**到目标输入框，确认后才发送；灰色提示文字不属于草稿 | 手表录音（16kHz mono）→ 上传 PC 桥接 → PC 端 STT → 经 Win32 模拟输入"追加"进目标窗口输入框；"确认后才发送"由桥接层控制提交动作 | ✅ 可行 | ① "按住"这个交互建议**改为屏幕长按 + 功能键短按触发**，因为按键事件能否截获待实测；② 必须严格区分"追加"与"覆盖"，且占位提示文本不得进入草稿缓冲 |
| 3 | **实时对话**：宠物页长按 SW2 开始/结束，使用用户配置的识别、对话、语音服务 | 长按进入对话态（录音→STT→LLM→TTS 流式回放），走手表扬声器或已配对蓝牙耳机 | ✅ 可行 | 手表只有 2 键，需重新分配：功能键长按=对话，表冠按压长按=系统关机（**不能占用**）。时延受 Wi-Fi 质量影响，需做"首字回包 <1.5s"的体验目标 |
| 4 | **形象与音效**：内置水豚噜噜，支持导入/生成自定义外观、状态视频和提示音；兼容固件支持独立下发音效 | 形象：内置 spritesheet + 支持导入 Petdex 格式 / 视频转帧；音效：App 内 AudioTrack/MediaPlayer 播放，资源包可热更新 | ⚠️ **降级** | **"兼容固件支持独立下发音效"无法实现**——没有固件控制权。能做的只有"App 内音效包下发"，系统提示音/闹钟音无法替换 |
| 5 | **组件中心**：预览、安装、移除游戏/工具/PC 数据组件；可用 PetUI 创作声明式或 WASM 组件 | 手表端组件宿主（JSON 声明式 + QuickJS/wasm3 脚本）+ PC 端生成与下发 + 桌面端管理 | ✅ 可行（**工作量最大**） | 32 位 ABI 限制 runtime 选型；组件沙箱与权限边界要提前定，否则一个组件能读通讯录就出事 |
| 6 | **设备设置**：桌面端管理音量、城市与 Wi-Fi 配对；设备默认长按 SW3 或从组件中心进系统设置 | 桌面端管理音量/城市/主题等业务参数；Wi-Fi 只做"引导跳转系统设置 + 回读 SSID 状态" | ⚠️ **部分降级** | 第三方 App **不能代用户完成 Wi-Fi 配网**（Android 10+ 限制，且 ColorOS 收紧）；"长按 SW3"在手表中不存在，改为"组件中心齿轮入口"或"长按功能键二级菜单" |

**按键重映射建议（2 键 + 表冠 + 触摸）**

| 物理输入 | 短按 | 长按 |
|---|---|---|
| 功能键（侧边长条） | 进宠物页 / 切下一个会话 | 语音输入（录音） |
| 表冠按压 | 返回（系统行为，不抢） | **保留系统关机菜单，不占用** |
| 表冠旋转 | 滚动组件列表 / 切换会话 | — |
| 屏幕 | 点击状态卡=展开任务气泡 | 长按宠物=进入实时对话（替代原 SW2） |

## 5. 总体架构

```
┌──────────────────────── 手表端 (Android APK, armeabi-v7a) ────────────────────────┐
│  UI 层     宠物页 / 任务气泡 / 组件宿主 / 对话页 / 设置页                          │
│  状态机    idle · thinking · running · waiting · done · error（+ 会话多路复用）      │
│  输入     触摸 / 功能键 / 表冠旋转 / 麦克风（AudioRecord 16k）                      │
│  输出     帧动画（Canvas/SurfaceView）/ 音效（AudioTrack）/ 震动（Vibrator）         │
│  组件     声明式 JSON 渲染器 + QuickJS(32bit) 或 wasm3 脚本宿主                     │
│  传输     【v2：可插拔 transport 层】BLE GATT（主，P9 待验证）+ Wi-Fi WS（备）         │
│          + mDNS 发现 + 断线重连 + 心跳 + seq/ACK 补传                               │
└───────────────────────────────────┬───────────────────────────────────────────────┘
                                     │ Wire 协议 v1（JSON，<4KB/帧，通道无关）
┌───────────────────────────────────┴────────────── 电脑端 Bridge ───────────────────┐
│  事件总线     统一事件模型 {session, agent, state, tool, text, ts}                   │
│  状态机       多会话聚合 → 单设备聚焦视图（自动选中"最近活跃"会话）                    │
│  适配器层     ① Claude Code ② Qoder ③ Codex ④ WorkBuddy ⑤ 豆包                     │
│  语音服务     STT（本地 vosk/whisper 或云）→ 文本 → 注入目标输入框（追加，非覆盖）      │
│  会话注入     Win32 SendInput / 剪贴板粘贴 + 回车；Esc 中断                         │
│  组件工厂    自然语言 → 组件 JSON/脚本 → 推送到手表；安装/卸载/版本管理               │
│  设置服务    音量/城市/主题/服务凭据（本地存储，不上云）                              │
│  传输        【v2：可插拔 transport 层】与手表端对称（BLE central / Wi-Fi WS server）  │
└──────────────────────────────────────────────────────────────────────────────────┘
```

> **v2 修订（2026-11-19）**：传输层从「WebSocket 单通道」升级为**可插拔 transport**（BLE 主 + Wi-Fi 备），协议抽出为 [contracts/protocol.md](../../contracts/protocol.md) 单点权威；分层与目录规范见 [architecture.md](architecture.md)。

### 5.1 事件模型（建议固定，避免五个适配器各写一套）

```json
{
  "v": 1,
  "session_id": "claude-3f2a",
  "agent": "claude-code",
  "state": "running",
  "tool": {"name": "Edit", "target": "src/app.ts"},
  "bubble": "写入文件 · app.ts",
  "ts": 1763430000000
}
```

`state` 只允许六值：`idle | thinking | running | waiting | done | error`。适配器负责把各自的原生事件折叠到这六态，**不要在手表端做语义推断**——手表只负责显示，越薄越稳。

### 5.2 传输选择

| 通道 | 适用 | 取舍 |
|---|---|---|
| Wi-Fi 直连 PC（WebSocket） | **主通道** | 手表有独立 Wi-Fi，不依赖手机；延迟最低；需同一网段 |
| 蓝牙经手机代理 | 无 Wi-Fi / 外出 | 带宽仅 80～120 KB/s，只传文本与状态；且依赖手机端转发 |
| eSIM + 公网中继 | 外出远场 | 需要鉴权与中继服务，成本高，**二期再做** |

建议一期只做 Wi-Fi 直连 + mDNS 自动发现（`_agentpet._tcp`），把"手动填 IP"作为兜底。

## 6. 五个 Agent 客户端的接入矩阵

| 客户端 | 可用接入点 | 能拿到的事件 | 完整度 | 工作量 |
|---|---|---|---|---|
| **Claude Code** | Hooks，支持 `command` / **`http`** / `mcp_tool` / `prompt` 类型；事件含 SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、PostToolUseFailure、PermissionRequest、Stop、StopFailure、Notification | 思考开始、每次工具调用及参数、权限等待、完成、API 错误 | ★★★★★ | 低（HTTP hook 直接 POST 到 bridge，零轮询） |
| **Qoder** | IDE/JetBrains 插件 12 个事件 + CLI hooks，支持 `command` 与 `http`；IDE 与 CLI 共用配置 | 同上，另含 SubagentStart/Stop、PreCompact、Elicitation | ★★★★★ | 低 |
| **Codex** | 生命周期 hooks / notify 钩子（Petdex 生态已验证该路径） | 思考、工具执行、等待、完成 | ★★★★☆ | 低～中（需按当前版本核对事件名） |
| **WorkBuddy** | 无公开 hooks；可从其**本地会话日志 + 审计日志** tail，翻译成六态 | 任务级状态、工具动作、完成/失败 | ★★★☆☆ | 中（日志格式变化即失效，要做容错与版本适配） |
| **豆包（PC 客户端）** | 无公开 hooks、无插件机制 | 只能从窗口标题/进程状态/输入焦点推测"在忙/空闲" | ★★☆☆☆（或 ★☆☆☆☆） | 中，且体验打折 |
| 通用兜底 | 窗口标题 + 进程 + CPU 活跃度 + 剪贴板变化 | 粗粒度"开工/收工" | ★☆☆☆☆ | 低 |

**结论**：一期的适配器应做 **Claude Code + Qoder + Codex**（三者体验一致、可信度高），WorkBuddy 作为二期，豆包放在"能跑到什么程度就什么程度"的兜底档，并在 UI 上明确标注该会话是"精状态"还是"粗状态"——这正是原设计那句"事件完整程度取决于适配器"该被产品化的地方。

## 7. "保留原始功能"的边界与风险

**能完整保留，因为方案不改系统**：不 root、不刷机、不写 system/boot 分区、不换 launcher、不改表盘。装一个普通 APK，卸载即完全还原。

**需要正视的副作用**：

| 风险 | 程度 | 缓解 |
|---|---|---|
| 省电策略杀后台，宠物状态断流 | 高 | 前台服务 + 常驻通知 + 息屏后靠"抬腕唤醒即拉取快照"，不追求全时在线 |
| 常亮显示导致续航从 5 天掉到 1～2 天 | 中高 | 默认"抬腕显示"，AOD 可选；用 LTPO 低频刷新；状态变化才重绘 |
| Shizuku/Dhizuku 在系统升级后失效 | 中 | 权限缺失时功能自动降级，不影响手表本体 |
| 侧载 App 触发 ANR 拖慢系统 | 中 | 单 Activity + singleTask + 严格内存预算（<120MB） |
| 用户误改 DPI 导致系统 UI 错位 | 低但烦 | 文档明确禁止改 DPI；提供恢复脚本 |

**明确不建议做的三件事**：root、替换桌面、期待系统表盘显示宠物。这三件都会直接违背"保留原始功能"。

## 8. 必做 PoC 清单（决定 Go / No-Go）

按优先级排列，建议 1～2 周内跑完。**每项都要在真机上出结论，不能靠文档推断。**

| # | 验证项 | 方法 | 通过标准 | 不通过时的备选 |
|---|---|---|---|---|
| P1 | **按键事件能否被 App 截获** | `adb shell getevent -l` 记录功能键/表冠的 keycode；再写最小 App 打 `onKeyDown` 日志对比 | 功能键短/长按都能拿到；表冠旋转能拿到 `AXIS`/`KEYCODE` | 全部放弃物理键，改"屏幕手势 + 桌面快捷图标" |
| P2 | **后台保活与息屏行为** | 前台服务 + 每 10 分钟打点，锁屏静置 8 小时看日志是否连续 | 8 小时内断流 ≤1 次 | 改为"抬腕唤醒后立即拉快照"的准实时模型 |
| P3 | **常亮/抬腕的功耗** | AOD 常开 vs 抬腕，各跑 24h 记录掉电 | AOD 日耗 ≤25%，抬腕 ≤12% | 只做抬腕；降低动画帧率到 8～12 fps |
| P4 | **Wi-Fi 长连稳定性** | 手表连 PC 的 WS server，心跳 30s，跑 24h 统计重连次数 | 断连 <3 次/天，重连 <2s | 加 mDNS 重发现；降级为轮询 HTTP |
| P5 | **麦克风录音** | `AudioRecord` 16kHz mono PCM，录 10s 回放 | 有权限、无爆音、能识别 | 改用系统录音 App 联动（体验变差） |
| P6 | **音频播放与音量** | AudioTrack 播放 1s 提示音；蓝牙耳机切换 | 扬声器与蓝牙都正常，音量可调 | 只做震动反馈（Z 轴马达可用） |
| P7 | **32 位 ABI 下的组件 runtime** | 在 armeabi-v7a 包中集成 wasm3 / QuickJS，跑一个简单脚本 | 能加载、能执行、内存 <20MB | 只做声明式 JSON 组件，砍掉脚本 |
| P8 | **官方"自定义硬件按键"指向侧载 App** | 设置 → 个性化 → 自定义硬件按键，选择宠物 App | 按键能稳定唤起 | 用桌面图标 + 通知快捷方式 |

**P1 的具体命令**（手表连底座后执行）：

```bash
adb devices
adb shell getprop ro.build.version.sdk      # 确认 API level
adb shell getprop ro.product.cpu.abi        # 确认 armeabi-v7a
adb shell wm size ; adb shell wm density    # 确认 378x496 / 320
adb shell getevent -l                       # 分别按功能键、转表冠、按表冠，记录 keycode
adb shell dumpsys window | findstr mCurrentFocus   # 观察系统按键行为
```

> 说明：OPPO 官方开发文档给的是 `minSdk 27 / Android 8.1`，但那是较早机型的口径，Watch 4 Pro（ColorOS Watch 6.0）的实际 API level 以 P1 实测为准。
